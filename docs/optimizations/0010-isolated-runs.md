# 0010 竞速改为"一个需求两个方案"，统一隔离执行

- 状态：已完成
- 日期：2026-11-20（创建）；2026-11-20（完成）
- 关联：同类功能统一分析（第六组）

## 背景

同类功能统一分析的第六组：子任务执行。用户此前问过："竞速模式是不是没有用对？一个任务下来可以给双方案。"

## 现状与问题

"在独立的 worktree 里跑一个 Agent，拿回它的改动"这件事，有两套实现：

| | `cove -p` 子进程（`workflows/worker.rs`） | 后台 Agent（`agents/background.rs`） |
|---|---|---|
| 使用者 | 竞速（`race.rs`）、自动化（`automation.rs`） | `agent(background=true)` |
| 怎么跑 | 另起一个 cove 进程：私有临时数据目录，最小配置（没有 MCP、Hooks、扩展），`--permission auto` | 同一进程里，在新建的 worktree 中运行；需要审批的操作排队等用户处理 |
| 费用 | 子进程的账本写在临时目录，跑完就删；费用只从子进程输出的 `[summary]` 文字里解析 | 经账本记入父会话 |
| 结果怎么拿回来 | 补丁：`/changes apply race:<id>:a confirm`（`git apply`） | 分支：`/status agents merge <id>`（git 合并） |

本机使用记录（111 个会话、572 条输入）：

- 竞速：0 次。`~/.cove/race/` 不存在。
- 自动化：0 个任务。QuoteHub 的 `state.json` 里 `specs` 为空。
- 后台 Agent：0 次。`agent` 工具一共用过 5 次，都在前台运行。

**P1 竞速几乎没法用。**
- 入口是 `/changes race <spec.json>`：要先手写一个 JSON 文件，写两个不同的提示（或者写 `models`）和至少一条验证命令。
- 结果要在 `/changes` 里按 `race:<run>:<a|b>` 去找。
- 用户想要的是"给一个需求，拿到两个方案，比较后选一个"，现在的设计是"给两段提示，比哪个能过验证"。

**P2 竞速和自动化的花费不进账本**：子进程的账本在临时目录里，跑完就删了；`/status cost` 看不到这部分开销。费用全靠解析子进程的输出文字，格式一变就丢。

**P3 两套执行器、两种取回结果的方式**：
- 子进程版没有 MCP 和 Hooks，权限固定是 auto；后台 Agent 和主任务用同一套工具和审批规则；
- 修 bug 或加能力要改两处，行为也不一致。

**P4 自动化从未用过。** 要先 `cove --automation add <spec> <项目目录>` 写入任务，再在操作系统里配定时任务调用 `tick`。功能本身没有问题，但使用门槛和场景都偏离日常用法。

## 目标

1. 竞速一条命令就能用：`/race <需求>` 得到两个方案，每个方案都经过同一组验证，附上改动摘要和费用，选一个应用。
2. 只有一个隔离执行器：竞速（以及保留下来的自动化）都用后台 Agent 的机制，在同一进程里运行。
3. 所有模型调用都进账本。

## 范围

- 做：
  - 新的 `/race` 入口；
  - 竞速改用后台 Agent；
  - 删除 `workflows/worker.rs`；
  - 自动化按决策处理（见待决策 2）。
- 不做：
  - 不改后台 Agent 取回结果的方式：它的结果是一个分支，合并后保留提交历史；竞速的候选只是补丁，只读预览、选一个应用，两种情况都合理；
  - 不改 `/changes apply` 应用前的检查（基线、干净工作区、补丁哈希）。

## 方案

**命令**

```
/race <需求>               两个方案并行，各自在新的 worktree 里实现
/race                      查看最近一次竞速的进度或结果
/changes show race:<id>:a  看方案 A 的补丁
/changes apply race:<id>:a confirm   应用方案 A
```

结果示例：

```
竞速 3f2a（12 分钟）：修复登录超时
  A  主模型 opus-5-5    验证 ✓ cargo test   改动 4 个文件 +86 -12   $0.42
  B  快速模型 sonnet-5-5  验证 ✗ cargo test   改动 2 个文件 +31 -4    $0.08
  /changes show race:3f2a:a 查看；/changes apply race:3f2a:a confirm 应用
```

**两个方案怎么来**：方案 A 用主模型，方案 B 用快速模型。没有配置快速模型（或和主模型相同）时，两个都用主模型，方案 B 的提示里要求"采用与最直接的做法不同的实现思路"。

**验证**：
- 不再要求手写验证命令：用 `safety/verify.rs` 的 `detect`，与自动验证门禁用同一套规则推断（`cargo test`、`npm test` 等）；
- 推断不出来时照样运行，结果标注"未验证"，由用户判断；
- 两个方案用同一组命令、同样只看退出码。"模型不能给自己打分"这条原则不变。

**执行**：
- 每个方案是一个后台 Agent（`editing` 类型），在从 HEAD 新建的 worktree 里运行，权限为 auto。理由：它改的是隔离的 worktree，不是用户的工作区，和现在子进程的权限一致；
- 需要按方案指定模型时，Agent 增加一个"本次运行使用的模型"选项；
- 两个方案跑完后，在各自的 worktree 里运行验证，捕获补丁，存到 `<data>/race/<id>/`，然后删掉 worktree；
- 费用经账本记入当前会话，来源记为 `race`。

**删除**：`workflows/worker.rs`（子进程执行器）、`race.rs` 里的 JSON spec 解析、`/changes race <spec.json>`。

## 决策记录

- 2026-11-20：按同类功能统一分析的建议顺序推进，这是第六组。（用户："继续"）
- 2026-11-20：两个方案由主模型和快速模型各做一个；没有配置快速模型时，退回同一模型做两次、第二个换一种思路。（用户）
- 2026-11-20：删除自动化。（用户）
- 2026-11-20：实施时的取舍（实施方）：
  - **隔离执行复用子代理的 `AgentHub::run`，而不是后台 Agent 的完整生命周期**。竞速需要的只是"在给定的 worktree 里跑一次、拿回结果"，不需要后台 Agent 的停放、恢复、收发消息和合并分支。`RunRequest` 加了三个选项：本次运行的模型、本次运行的审批者（竞速用后台 Agent 的 `BackgroundAuthorizer`，`auto` 模式、判定范围是方案自己的 worktree）、"任务外运行"（花费进账本的后台槽，由会话在命令结束时吸收）；
  - **账本来源不另记为 `race`**。账本在 provider 边界记账，来源是固定的；改成按调用区分，需要让请求带上来源，改动面大（0005 做过同样的取舍）。竞速的调用以会话来源记入，费用计入当前会话；
  - **未验证的方案不能直接应用**。`/changes apply` 对"没有任何验证记录"的补丁一律拒绝，这是原有的安全规则（有专门的测试），不为竞速放宽。推断不出验证命令的项目，可以配置 `done_verify_commands`，或 `/changes export` 后自行检查；
  - **方案的调用上限沿用 `subagent_max_iterations`**（默认 60），不再像子进程那样固定 12 次。
- 2026-11-20：`~/.cove/backups/0010-*` 下的自动化数据的备份已删除。（用户："一起删了"）
- 2026-11-20 收尾核对（[0014](0014-audit-fixes.md)）：
  - 方案用的是 `general` 类型（方案里写的"editing"不对）；
  - 查看补丁用 `/changes diff`，不是 `/changes show`；
  - "取消时清理两个 worktree"没有测试；
  - 核对时发现方案超时会丢掉运行（花费不入账、活动状态不结束），结果也总是提示应用 A，已在 0014 修正。
