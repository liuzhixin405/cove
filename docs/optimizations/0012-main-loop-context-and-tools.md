# 0012 主流程第一批：上下文长度和无效轮次

- 状态：已完成
- 日期：2026-11-20（创建）；2026-11-20（完成）
- 关联：主流程优化调研（2026-11-20 对话记录，含 Claude Code、Codex、OpenCode、Gemini CLI 的做法）

## 背景

用户要求专心研究主流程的优化。调研结合了本机数据（`trace.jsonl` 3427 次模型调用、3813 次工具调用，费用账本，111 个会话）和同类 agent 的源码及文档，列出 12 项建议。用户确认先做第一批（1、2、3、9、10）："开工"。

## 现状与问题

**P1 长上下文是最大的成本和延迟来源。**

| 上下文 | 调用次数 | 单次耗时中位数 |
|---|---|---|
| < 5 万 | 1115 | 4.2 秒 |
| 10–20 万 | 489 | 7.9 秒 |
| 30–40 万 | 294 | 9.7 秒 |
| 40–50 万 | 222 | 11.4 秒 |
| ≥ 50 万 | 379 | 14.2 秒 |

64% 的输入 token 出现在上下文 ≥ 30 万的调用里，这些调用只占 26%。原因有三个：

- **旧工具输出的保护范围随窗口无上限放大**（`engine/tool_output.rs`）：最近 `PROTECTED_TOKENS = 5 万 × 窗口/12.8 万` 的工具输出不外置。1M 窗口下是约 39 万，最近 39 万 token 里的工具输出永远留在上下文里。同一文件里单条结果上限的放大倍数有封顶（`MAX_SCALE = 4`），这一处漏了。对比：OpenCode 保护 4 万，Gemini CLI 保护 5 万，都不随窗口变化。
- **压缩阈值接近窗口上限**：估算值超过上下文预算（窗口的 85%）的 90% 才压缩，1M 窗口约是估算 76.5 万。
- **token 估算偏低**：估算只算消息，不含系统提示和工具定义，字节换算也偏粗。实际/估算的比值中位数 1.31，p90 是 2.38。例如 11-06 的一次压缩，估算 49.8 万，实际发送 92.1 万。所以触发时实际已经接近窗口上限。

**P2 模型用 shell 做文件操作。** 665 次 shell 调用里，`cat >` 写工作区文件 40 次（另有 70 次写临时脚本），`sed -i` 改文件 22 次，`sed -n` 读行区间 25 次，`grep -n`、`grep -rn` 49 次。系统提示只要求"读和搜索用专用工具"，没提写和改。走 shell 要多一次审批、绕开编辑前的核对；在 Windows 上 shell 调用的中位耗时 9 秒，文件工具是毫秒级。

**P3 memory 工具常因漏掉 `scope` 失败。** `missing field scope` 出现 6 次以上，连续失败还触发过护栏。工具说明写了"每个动作都要 scope"，模型照样会漏。

## 目标

1. 长会话的上下文明显变小：大窗口模型在 40 万左右就压缩，旧工具输出及时外置。
2. 压缩时机按真实 token 数判断。
3. 写和改文件走文件工具。
4. memory 工具不再因为漏了 scope 失败。

## 范围

- 做：上面 4 项。
- 不做（第二批）：后台预压缩、缓存 TTL、边流边执行。

## 方案

**1. 工具输出的保护范围固定为 5 万 token**，不随窗口放大；"至少能省 3 万才改写历史"的门槛不变。单条结果的上限照旧按窗口放大（封顶 4 倍）。

**2. 估算按真实用量校准。**
- 每次模型调用返回后，用服务端报告的输入 token 数除以本次请求前的估算值，得到校准比例，限制在 0.5–3 倍之间；
- 之后的估算乘以这个比例。直接用"上次实际值 + 新消息估算"更准，但外置旧输出会改写历史，那个基数就失效了；比例不受这个影响；
- 服务端没有报告用量时（部分本地模型），比例保持不变。

**3. 自动压缩阈值：预算的 90%，和 40 万 token，取较小者。**
- 40 万来自本机实测：超过 40 万后单次调用明显变慢（11.4 秒起，是 5 万以内的 2.7 倍以上）；
- 小窗口模型（预算 × 90% < 40 万）不受影响；
- 原来的"上下文已约 40 万，响应会变慢，建议 /compact"提醒失去意义，一并删除。

**4. 写和改文件走文件工具。**
- 系统提示补充：创建或改写工作区文件用 write，修改用 edit，不要用 `cat >`、heredoc、`tee` 或 `sed -i`；
- 护栏：shell 命令是对工作区文件的 `cat >`、`tee`、`sed -i`、`sed -n` 时，在结果后附一句提示，每个任务每种只提示一次。写到临时目录（`/tmp`、`$TEMP`）的不提示。

**5. memory 工具的 scope 可以省略。**
- read、update、delete 只给 id 时，按 id 在两个范围里找；唯一时用它，两边都有时报错要求写明；
- add、list、search 省略时默认 project；
- 工具说明相应更新。

## 影响范围

- 文件：`src/engine/tool_output.rs`、`src/engine/agent.rs`、`src/safety/gates/guard.rs`、`src/tools/extension_tools.rs`、`docs/reference.md`。
- 行为变化：
  - 大窗口模型的长会话更早压缩（约 40 万）；
  - 旧工具输出更早外置成文件；
  - 用 shell 写或改工作区文件时，结果后面会多一句提示；
  - memory 工具可以不写 scope。

## 验证

- 单元测试：
  - 1M 窗口下保护范围仍是 5 万；
  - 校准比例按真实用量更新、有上下限，没有用量时不变；
  - 估算超过 40 万时触发压缩，小窗口仍按 90%；
  - shell 提示：`sed -i`、写工作区文件的 `cat >` 会提示，写 `/tmp` 不提示，同一任务只提示一次；
  - memory：省略 scope 时 read 能找到全局条目，add 默认 project。
- 全量 `cargo test`。

## 决策记录

- 2026-11-20：先做第一批（1、2、3、9、10）。（用户："开工"）
- 2026-11-20：压缩阈值用 40 万 token 的固定值，不做配置项：它来自实测的延迟拐点，和模型窗口无关；以后需要再加配置。（实施方）
- 2026-11-20：实施中补的一处（实施方）：压缩时保留的最近消息原来最多是"预算的一半"，1M 窗口下是 42.5 万，本身就超过 40 万的新阈值，会导致每轮都再压缩一次。改为不超过压缩阈值的一半（20 万）。
- 2026-11-20 收尾核对（[0014](0014-audit-fixes.md)）：
  - id 在两个范围都存在时原来默默用了 project，没有按方案报错；
  - 压缩保留部分的上限原来按原始估算算，校准比例大于 2 时可能连续压缩；
  - shell 提示把 `src/tmpl/` 这类路径当成临时目录。
  这些已在 0014 修正。

## 验证结果

- **改动**：
  - `tool_output.rs`：保护范围固定 5 万；
  - `agent.rs`：校准比例（`calibration`）、压缩阈值（`compaction_threshold`，预算 90% 与 `SLOW_TOKENS = 400_000` 取较小者），删除 40 万提醒（`context_warning`）；
  - `context.rs`：`prepare` 增加保留上限参数；
  - 系统提示增加写和改文件的要求；
  - `guard.rs`：增加 `file_tool_hint`，每个任务每种提示一次；
  - memory 工具的 `scope` 改为可选，并按 id 推断。
- **新增测试**：
  - 单元测试：1M 窗口下旧输出照样外置，最新一条保留（改动前，39 万的保护范围会让 21 万 token 的旧输出一条都不外置）；压缩阈值；校准比例的上下限，以及用量太小或未报告时不校准；shell 提示的 6 种命中和 5 种不命中（临时脚本、`2>&1`、`tee /dev/null` 等）；memory 省略 scope 时按 id 找到全局条目，默认 project；
  - 集成测试：`million_window_compacts_where_calls_slow_down`：1M 窗口、约 46 万 token 的历史会先压缩，压缩后低于 20 万。
- **改写的测试**：
  - `million_window_does_not_compact_before_new_threshold` 改为 `…below_the_slow_threshold`，历史改为约 29 万；
  - `memory_can_be_read_after_repeated_missing_scope_errors` 改为 `memory_reads_without_scope_using_the_short_id_of_the_index`；
  - `memory_definition_requires_scope_for_every_action` 改为 `memory_scope_is_optional_and_found_from_the_id`。
- **删除的测试**：`large_context_warns_once_with_compact_and_new_hints`（提醒已删除）。
- `cargo test` 全部通过：单元测试 385 个（另有 4 个忽略），集成测试 215 个。
- 只对改动过的文件，通过标准输入运行了 rustfmt；`cargo build --release` 完成。

## 遗留

- **效果要用新数据验证**：用一两天后，用 `trace.jsonl` 再统计"上下文 ≥ 30 万的调用占比"和单次调用延迟的分布，与本文的表格对比。
- **压缩会更频繁**：大窗口的长会话以前几乎不压缩，现在约 40 万就压缩，每次 20–85 秒。第二批的"后台预压缩"就是为了把这段等待藏起来。
- **第二批**：后台预压缩、缓存 TTL（先验证 Bedrock 是否支持 1 小时）、边流边执行。
