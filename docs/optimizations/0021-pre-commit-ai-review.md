# 0021 项目规则：把踩过的坑沉淀下来，写代码时遵守，提交前检查

- 状态：已完成
- 日期：2026-11-20（创建）；2026-11-20（完成）
- 关联：[0003](0003-remove-skill-auto-learning.md)（技能自动学习为什么失败）、[0008](0008-memory-injection-and-notes.md)（记忆注入）、[0020](0020-agents-rules.md)（cove 仓库自己的 AGENTS.md）

## 背景

用户原话：
- "可以加一个提交代码之前的 ai-review，把这个 agents 算进去。"
- "agents.md 是为当前项目服务的，但是这种方式可以借鉴到使用 cove 的所有项目中，这是提升 cove 作为智能体代码的一种手段。"

0020 给 cove 仓库写了一份禁忌清单，这套做法本身应该做进 cove，让每个项目都受益：

- 踩过的坑沉淀成规则；
- 规则在写代码时生效；
- 提交前按规则检查。

## 现状与问题

**cove 已经在记坑，但记下来照样会再踩。** 本机 7 个项目共 193 条记忆，dream 整理出 6 条"rules and patterns"。内容不错，例如"测试不要列系统临时目录"、"直接推 staging 会被拒，报告给用户"。还会再踩，有四个原因：

1. **规则淹没在流水账里**：规则和会话 id、日期、commit hash、一次性排查过程混在一起。最大的项目里，规则分成了 3 条记忆，因为 dream 改不了主条目，只能追加补充。
2. **用到的时候不在上下文里**：项目记忆超过 8 KB 后，每个任务只带 5 条和需求文字相关的，每条最多 2 KB（`memory/recall.rs` 的 `INLINE_LIMIT`、`TOP_K`、`RELEVANT_ENTRY_LIMIT`）。坑往往踩在动手时（跑命令、写文件），需求里没有这些词，规则就匹配不上。
3. **没人检查**：提交有两条路——用户的 `/commit`（`commands/project.rs`）和模型的 `git commit`（`safety/gates/commit.rs` 的门禁）——两条都只跑构建和测试。门禁甚至只在配置了验证命令时才存在。任务结束时的自审（`safety/gates/review.rs`）默认关闭，提示词里还写着 "Do not comment on style or naming"，项目规则会被当成风格问题跳过。
4. **换电脑就丢**：记忆按项目的本机路径区分（`memory/store.rs:374` 用路径哈希做键）。同步 `~/.cove` 也没用，路径一变就对不上；团队成员和其他工具也看不到。

**同类工具的做法**：
- Windsurf 把 Memories 和 Rules 分开；
- Cursor 把项目规则放在 `.cursor/rules/`，能从对话生成规则，BugBot 按规则审查；
- Cline 用 `/newrule` 写 `.clinerules`；
- Claude Code 的记忆专门记用户的纠正，写明原因和用法。

共同点：**规则和事实分开；规则短、是明确的要求、始终生效；放在项目目录里。**

**0003 的教训**（技能自动学习从来没起过作用）：
- 学到的是一次性的事件；
- 要审批，结果没人批；
- 每个任务多花一次后台调用；
- 和记忆重复。

## 目标

- 每个用 cove 的项目都有一份规则文件，跟着仓库走，换电脑、换人都能用；
- 规则从两处来：用户的纠正，以及反复出现的问题。不新增后台调用；
- 规则在每个任务里完整生效，不靠相关性匹配；
- 提交前，AI 按规则和真实缺陷审查真正要提交的内容，发现问题就不提交。

## 方案

### 1. 规则文件 `.cove/rules.md`

- 位置：`<git 根目录>/.cove/rules.md`，不在 git 里时用工作区目录。工作区过宽（家目录、盘符根）时不启用。cove 已经用 `<项目>/.cove/skills/` 放项目技能，这里沿用同一个目录。
- 格式：一个说明头，加上每条规则一行 `- 规则（YYYY-MM-DD）`。可以直接手改，cove 只认 `- ` 开头的行。
- 新模块 `memory/rules.rs`（`ProjectRules`）：
  - 读取；
  - 添加：去重，每条最多 300 字，最多 60 条，写入用 `persist` 原子写加锁，先过 `screen`，不收密钥；
  - 删除；
  - 记录本进程新增的规则，用来提示。
- 生效：
  - `.cove/rules.md` 加进项目说明文件列表（`engine/prompt.rs` 的 `INSTRUCTION_FILES`），和 AGENTS.md 一样进入系统提示的 "Project instructions"，安全上也同等对待：是项目方的指令，不能越过安全规则；
  - 会话中途新增的规则，在下一个任务开始时作为提示带给模型。
- 不想提交的项目：`/rules local` 把它加进 `.git/info/exclude`。

### 2. 规则从哪来（复用已有调用，不新增后台调用）

- **用户的纠正**：每个任务结束后的记忆提取（`memory/extract.rs`）原样运行，输出格式加一种 `---RULE---` 块，只收用户对做法的纠正，或明确说的长期规则（"别这样"、"以后都……"、"又错了"），用用户的语言写成一句"不要……，改为……"。一次就记，因为这是用户明说的。
- **反复出现的问题**：dream 加一个 `project_rules` 工具（list / add），第 3 步改成：同一类"问题 → 尝试 → 失败 → 解决"在**至少两个会话**里出现，才写成一条规则；一次性事件不写。已有的"rules and patterns"记忆，把里面仍然成立的规则逐条搬进规则文件，不再写新的"rules and patterns"。
- **手动**：`/rules add <文字>`。
- 规则写入后自动生效，不需要审批（用户决定）。下一个输入提示前打印一行"记下一条项目规则：……（/rules 查看或删除）"。

### 3. 提交前 AI 审查

- 审查核心抽成 `review::Reviewer`，结果是 `Verdict`：
  - `Passed`：通过；
  - `Issues`：发现问题；
  - `Skipped`：审查没跑完，不拦截，免得网络一抖就提交不了。
- 审查标准（`CRITERIA`）：真实缺陷，加上项目规则——系统提示里的 "Project instructions"，以及审查时读到的最新 `.cove/rules.md`。违反规则就算问题，并引用那条规则；没有规则覆盖的风格不提。任务结束时的自审也用这套标准。
- 审查对象：`git diff --cached`，最多 40 KiB。附上当前需求，结论用需求的语言写。
- 模型：快速模型，没配置时用主模型。（用户决定）
- 模型的 `git commit`：门禁先跑验证（如果有），再审查。有问题就拦下，问题交回模型：真实的问题修掉再提交，认为不成立的告诉用户原因，不要绕过。同一份暂存内容只判定一次。现在门禁在"有验证器或开了审查"时都会存在。
- `/commit`：验证通过后、提交前审查。有问题就不提交，提示修改后重新运行，或用 `/commit --no-review` 跳过。（用户决定）
- 配置 `commit_review`：默认 `on`（用户决定）；`off` 关闭；`auto` 只审改动不少于 40 行的提交。项目配置里设成 `off` 不需要信任，其他值需要信任，规则和 `commit_gate` 一样。

## 范围

不做：
- 不自动改 AGENTS.md、README 等用户自己写的文件；
- 不审查推送（提交时已经审过）；
- 不做自动修复；
- 不给规则设过期时间（dream 合并和清理就够了，需要时再加）；
- 不迁移旧的"rules and patterns"记忆条目本身（dream 会逐步把规则搬出来；条目留着无害）。

## 遗留

- 后台记下的规则在"下一个输入提示前"才显示。提取大约需要 5–20 秒，所以常常是你输入下一句、按回车之后才看到那一行提示。
- 规则没有过期机制。过时的规则靠 dream 合并，或者 `/rules remove` 删除；以后真有规则堆积，再加"多久没被审查引用就提示清理"。
- "审查指出、被修掉的问题，第二次出现时升级为规则"没有单独实现，靠 dream 读最近会话时一并发现（审查结果作为工具结果留在会话里）。效果需要实际使用一段时间后再看。
- 旧的"rules and patterns"记忆条目不会自动删除；dream 会把里面仍然成立的规则逐条搬进规则文件。
- 实施中有一次测试"卡住"，原因是命令开头误写了 `cat > /dev/null`，它在等标准输入，与代码无关。
