# 0032 按"有没有进展"止损：连续多轮没有新改动、新信息时停下汇报

- 状态：已完成
- 日期：2026-11-23（创建）；2026-11-23（完成）
- 关联：0012（无效轮次）、0023（真实模型评测）、0024（无人值守时拒绝调用而不终止任务）；`src/engine/agent.rs`、`src/safety/gates/guard.rs`、`src/agents/subagent.rs`、`src/session/snapshot.rs`

## 背景

前期调研的说法是：有一个会话里连着两次要求"不用再试了"，另一个会话里也有一次；任务耗时 p90 为 443 秒，单个任务最多调用了 586 次模型；现有熔断只看同一工具是否重复，不看有没有进展。设想是：连续 N 次调用既没有新的改动也没有新的信息时，停下来汇报已经做了什么，并给出几个选项。

本文先用本机数据核实这些说法（结论是一半对、一半不对，见下一节），再设计一个**并入现有熔断和调用上限**的止损机制，不另起第三套。

## 现状与问题

### 一、现有的止损机制

| 机制 | 位置 | 触发条件 | 触发后 |
|---|---|---|---|
| 调用次数上限 | `agent.rs:1454` `run_loop` | 本轮模型调用达到 `max_iterations`（默认 200，`config/mod.rs:973`） | 交互：问"再继续 200 次？"；否则 `wrap_up`（无工具总结一次，`agent.rs:563`）后报 `Error::Limit`，提示 `/continue` |
| 任务时限 | `app/mod.rs:1405` `drive` | 总时长超过 `max_turn_minutes`（默认 3600 秒） | 取消任务，报 `Error::Limit`，不总结 |
| 自动验证轮数 | `agent.rs:30` `VERIFY_ROUNDS = 3` | 收尾时验证失败 | 前两次把失败详情交回模型继续改，第三次失败就结束任务（报"验证未通过"） |
| 重复失败熔断（guardrail） | `guard.rs:200` | 同一工具 30 秒内失败 3/5 次；同一调用失败 2/5 次；同一工具连续失败 3/8 次；读类工具结果相同 2/5 次 | 前一档在结果后附警告，后一档**拒绝这一次调用**，模型收到失败结果 |
| 循环检测 | `guard.rs:317`、`366` | 同一修改类调用在最近 14 次里出现 10 次；同一工具换参数在最近 12 次里出现 10 次（输出或目录在变就不算）；同一输出在最近 40 次结果里出现 8 次 | 拒绝该调用；第 2 次检测到时交互询问"让 agent 继续吗？[y/N]"；第 5 次进入 `stopped`，之后所有工具调用都被拒绝，提示模型直接总结 |
| 无活动提醒 | `guard.rs:427` `STALL_THRESHOLD = 60` | 60 次工具调用里没有成功的 read/write/edit | 只在结果后附一句提醒 |
| 失败批次升级 | `routing.rs:352` | 连续三批工具调用全部失败、或验证失败 | 从快速模型切回主模型，不止损 |
| 子 Agent 上限 | `subagent_max_iterations`（默认 60） | 子 Agent 模型调用达到上限 | `exit: max_iterations` |

所以"现有熔断只看同一工具是否重复"**不准确**：循环检测已经看"同一输出反复出现"和"换参数但输出不变"，也有一个 60 次的无活动提醒。真正的缺口是下面几条。

### 二、缺口

**P1 guardrail 的拒绝不会升级。** guardrail 拒绝调用时直接返回（`guard.rs:323` `Err(block) => return Some(block)`），不经过 `hit()`，不计入检测次数，所以不会询问、也不会停。模型可以一直调用被拒绝的工具，每次都花一次模型调用，直到 200 次上限。11-05 的一个任务就是这样：`edit` 报 "file drifted since its previous edit" 约 10 次，之后又被 guardrail 以 "edit failed 5 times within 30 s"、"edit failed 8 times in a row" 拒绝约 10 次，模型仍在继续调用（见下面的 C3）。

**P2 `stopped` 不结束任务。** 循环检测第 5 次后只是拒绝所有工具调用，靠模型自觉不再调用工具；模型继续调用时，每一轮都花一次模型调用。没有一条"由 cove 主动收尾"的路径，只有调用上限才会触发 `wrap_up`。

**P3 "活动"的定义太粗。** 无活动提醒只认成功的 read/write/edit：
- 用 shell 改文件（`cat > /tmp/x.py` 再运行）不算活动，C2 整个任务 58 次 shell 调用都是这样改的代码；
- 反复读同一个文件算活动。

**P4 没有"新信息"的概念。** 循环检测按"同一调用""同一输出"计数，换着参数跑、每次输出都略有不同（时间戳、耗时、端口号）时检测不到；而同一个错误在不同命令下反复出现（比如连接被拒绝），每条命令都不一样，也检测不到。

**P5 子 Agent 没有任何循环检测。** `ToolGuard` 只在主任务的 `Assembly::new`（`gates.rs:448`）里装配，子 Agent 只有 60 次的调用上限。

**P6 收尾路径不统一。** `wrap_up` 的提示写死为 "model call limit reached"；`-p` 模式下 `Error::Limit` 不打印 `[summary]`（`ui.rs:607` 只在 `Ok(report)` 时打印），评测会把这种结束判为 `unknown`。

**P7 trace 里任务的 `model_calls` 是会话累计值。** `diagnostics.rs:608` 写的是 `session.accounting.model_calls`，不是本任务的调用次数。前期调研的"单个任务最多 586 次"就是把它当成了单任务值（见下）。

数据范围：`~/.cove/trace.jsonl`，2026-10-27 到 2026-11-23，492 条任务记录、3921 次模型调用、3909 次工具调用、14 次压缩；会话 122 个，另有 14 个压缩前的存档。trace 里没有会话 id，按"两条任务记录之间的模型和工具记录属于后一个任务"切分，再用工具名序列在会话里做精确匹配，135 个工具调用不少于 8 次的任务全部对上了会话。

**任务规模（每个任务按切分出的模型调用记录计数，含子 Agent 的模型调用）**

- "单个任务最多 586 次"**不成立**：586 是一个会话跨多个任务的累计值（P7）。单任务最多 164 次，那个任务委派了 11 个子 Agent，主任务自己只有 54 次工具调用。
- "p90 443 秒"基本成立（实测 446 秒）。耗时最长的是 3600 秒，正好等于默认任务时限。
- 调用次数 ≥ 50 的任务 9 个，≥ 100 的 2 个，**没有一个任务碰到 200 次上限**（E5001 出现 0 次）。非正常结束的 66 个任务里，用户取消（E5002）18 次，网络错误（E2001）14 次。
- 工具调用失败 202 次，占 5.2%。任意连续 20 次工具调用里，只要没有成功的 edit/write，失败最多 6 次。

**"不用再试了"这类话**：在全部会话和存档的用户消息里搜"不用再试、别试了、不要再试、停、算了、放弃、反复、一直在、卡住"等，只命中 3 条，都是要求不用再试、把已经完成的部分总结一下：

- 其中两条在同一个会话里，是**同一句话发了两次**：第一次发出后，cove 自己连续失败 8 次（网络错误 E2001、压缩失败"待压缩内容超过安全大小"E5003、旧版本的 E5004），只好重发。它之前的三个任务分别跑了 55、32、19 分钟，在下载本地模型、逐个跑 llama-bench，单次 shell 调用 120–160 秒，有两次超时；**每次调用都有新结果，不是原地打转**，不满的是时间太长、做的事超出了要问的问题。

**数据的含义**：
1. 主模型（本机 98% 的调用是 Opus）大多会自己停，真实的原地打转只有 C3、C4 两段，都是"同一错误被反复拦截"；
2. 按这里的进展定义，真实任务里最长的无进展段是 6 次工具调用（C4），其余都不超过 4 次；
3. 本机几乎没有用 DeepSeek 和本地模型跑长任务的数据，而 cove 主要搭配 DeepSeek 使用，弱模型更容易打转，阈值的"该停时停"这一面只能靠评测用例检验，不能靠本机数据标定。

## 目标

1. 模型连续多轮既没有改动、也没有拿到新信息时，cove 主动停下：交互模式给出选项，`-p` 模式总结后结束，不直接杀掉。
2. 停下时如实汇报：做了什么、试过什么、卡在哪个错误上、需要用户提供什么。
3. 不误伤：本机 135 个任务按新规则回放，不触发停止；长时间构建、真正需要多次尝试的调试不受影响。
4. 和现有机制合并：guardrail 和循环检测负责"拦下这一次调用"，新的进展判断负责"这个任务要不要停"，调用上限和它共用一条收尾路径。止损不再分散在三处。
5. 子 Agent 也适用。

检验标准：见"验证"，包括单元测试、模拟模型的集成测试、两个新评测用例，以及对本机 trace 的回放。

## 范围

- 做：
  - 进展的定义和计数（按轮）；
  - 达到阈值后的处理：交互询问、`-p` 和子 Agent 收尾；
  - 合并现有的升级逻辑：去掉 `ToolGuard` 里的 `hits`/`ask`/`stopped` 和 60 次无活动提醒，guardrail 的拒绝计入"无进展"；
  - 统一 `wrap_up`，`-p` 下因止损或上限结束时也打印 `[summary]`；
  - trace 增加本任务的调用次数和止损记录；
  - 文档、测试、评测用例。
- 不做：
  - **按时间或花费止损**（C6 的真实诉求）：它和"有没有进展"是两回事，阈值也要另行调研（多长算长、要不要按费用），另开文档，见 D6；
  - 用模型判断有没有进展（OpenHands 之外也有人让模型自评）：多花钱，而且判断本身不稳定；本文只用本地可计算的信号；
  - 改 guardrail 和循环检测本身的阈值：本机数据里它们拦得对，问题在拦下之后没人叫停；
  - 改调用上限 200 的默认值：没有任务碰到过它，它只作为最后的硬上限。

## 调研与参考

凭公开资料和源码印象，具体细节以各项目当前版本为准：

- **OpenHands `StuckDetector`**（`openhands/controller/stuck.py`）：只看最近的动作和观察，检测五种模式：同一动作得到同一观察重复 4 次；同一动作得到错误观察重复 3 次；模型反复说同一段话、中间没有任何工具调用（独白循环）；两组动作和观察交替出现 6 步（A-B-A-B）；上下文压缩反复失败。比较时忽略事件 id 和时间戳。无人值守时直接以 `AgentStuckInLoopError` 结束；新版本在交互界面里提供"从循环开始前恢复 / 继续 / 停止"的选择。**取舍**：它比较的是"动作 + 观察"的相等性，能抓住 C3、C4，但抓不住"每条命令不同、错误相同"；我们借用"忽略时间戳比较""错误重复""独白循环""交替"这几个思路，另外加上"工作区有没有变化"这个它没有的信号（OpenHands 在沙箱里跑，没有 cove 这样的工作区快照）。
- **SWE-agent**：用花费止损，`per_instance_cost_limit`（每个实例的费用上限）、`total_cost_limit`，以及调用次数上限；超限时以 `exit_cost` 等原因结束，并自动提交当前的改动（autosubmit），不丢已有成果。**取舍**：花费和次数是兜底，cove 已有调用上限；借用"止损时保留并汇报已有成果"。
- **Claude Code**：无人值守模式和 SDK 有 `--max-turns`/`maxTurns`，交互模式靠用户随时按 Esc 打断；公开资料里没有看到专门的卡住检测。
- **Codex CLI**：靠用户打断和审批策略，`exec` 模式跑到模型自己结束；公开资料里同样没有看到专门的卡住检测。
- **cove 自己**：0012 把"无效轮次"作为第一批处理过（工具输出外置、memory scope、写文件走文件工具），解决的是浪费，不是止损；本文接着解决"拦了之后没人叫停"。

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 只调循环检测的阈值 | 把 10/14、8/40 调小 | 仍然抓不住"命令不同、错误相同"，调小会误伤正常的换参数尝试 |
| B. 在 `ToolGuard` 里加第三种检测 | 新增进展计数，和现有的 hits 并列 | 三套升级逻辑叠在一起；`ToolGuard` 不在子 Agent 里；hook 只能拒绝调用，不能结束任务 |
| **C. 引擎里统一记进展，hook 只负责拦单次调用（采用）** | `engine/progress.rs` 在每轮结束后判断有没有进展；guardrail 和循环检测的拒绝作为"无进展"的输入；达到阈值时走和调用上限同一条收尾路径 | 要改 `run_loop` 和 `ToolGuard` 的分工，改动面比 B 大 |

## 方案

### 1. 以"轮"为单位计数

一轮 = 一次模型回复 + 这次回复里的全部工具调用及结果。一轮里只要有一个调用有进展，这一轮就算有进展。按轮而不是按工具调用计数：模型一次并行读 10 个文件不应该被算成 10 次。

另外两种情况也算一轮：
- 模型只回复文字、被收尾催促（`finish_nudge`）送回继续：算一轮**无进展**（对应 OpenHands 的独白循环）；
- 收尾验证失败、把失败详情交回模型：按下面第 2 条的"验证"判断。

### 2. 进展的定义（全部本地计算）

在一个任务内维护几个"见过"集合，任务开始时清空。一轮里出现下面任何一项，就算有进展：

| 信号 | 判断 | 针对 |
|---|---|---|
| **工作区变了** | `edit`/`write` 成功，且 `(路径, 新内容的 SHA-256)` 没见过；或在"确认"时（见第 3 条）工作区快照的树哈希不在本任务见过的树里 | 改代码；A→B→A 来回改不算进展；C2 用 shell 改文件也能认出来 |
| **新信息** | 成功的调用，键 =（工具名，归一化的主参数，归一化输出的摘要）没见过 | 读新文件、新的搜索结果、命令输出变了；C5 的 13 张图因为路径不同都算新信息 |
| **新错误** | 失败的调用，错误签名 =（工具名，归一化的前两行错误内容，退出码）没见过 | 换了做法后错误变了算进展；同一个错误换着命令出现，不算 |
| **验证结果变了** | 自动验证的结论或失败详情的摘要和上一次不同 | 修好了一部分测试也算进展 |
| **用户给了新输入** | 插话（steer）、`ask_user` 得到回答、审批时用户写了理由 | 用户说了话就重新计数 |

归一化：去掉 `\\?\` 前缀（`paths::key`），数字替换成 `#`，7 位以上的十六进制串替换成 `H`，只取前 4 KB 和后 1 KB 计算摘要。这样"同一个错误、不同的耗时和端口号"算同一个，而 C5 那种不同路径的结果因为主参数不同不会被合并。

**不算进展**：
- 被 guardrail、循环检测、计划模式、拒绝规则拒绝的调用（解决 P1）；
- 结果和以前完全一样的调用；
- 记账类工具：`todo`、`memory`、`skill`。它们既不算进展也不清零；一轮里只有它们时，算这一轮无进展（防止靠更新 todo"保持活跃"）；
- `agent`（子 Agent）：按它的结果摘要判断是否新信息；子 Agent 改了文件，会在确认时体现在工作区快照里。

### 3. 阈值和两级处理

- 连续 **6 轮**无进展：在这一轮的工具结果后附一句提醒（替换掉现在的 60 次无活动提醒）：
  `[progress] 最近 6 轮没有新的改动或新信息（反复出现：<最常见的错误签名> ×N）。先说明是什么挡住了你，再换一个不同的做法；如果缺的是外部条件（服务、权限、依赖），直接说明并结束。`
- 连续 **12 轮**无进展：先**确认**，再止损。
  - 确认：取一次工作区快照（`snapshot.rs` 已有的 `snapshot()`，返回树和"是否需要新快照"），树哈希不在本任务见过的树里，就说明 shell 或子 Agent 改了文件（C2），计为进展、清零；快照不可用（非 Git 目录太大、已因为太慢而关闭）时跳过确认，直接按无进展处理。只在第 12 轮做一次，不给每轮增加开销。
  - 止损：见第 4 条。

阈值依据：本机 135 个任务里最长的真实无进展段是 6 次工具调用（C4），轮数只会更少，12 轮留出了两倍以上的余量；C3 那段约 20 次的打转会在第 12 轮被叫停。

做成配置项 `stall_rounds`（默认 12，提醒在它的一半；0 关闭），和 `max_iterations` 一样属于不需要信任就能生效的限额。

### 4. 止损时做什么

先在本地整理一份事实摘要，不靠模型回忆：
- 本任务用了几次模型调用、几轮没有进展；
- 改过的文件（工作区快照和任务开始时比较，或 edit/write 记录）；
- 出现最多的 3 个错误签名及次数、对应的命令；
- 跑过的检查及结果（`Evidence` 已有）。

**交互模式**（有 `UserInput`）：在发起下一次模型调用之前暂停，显示摘要并询问：

```
[没有进展] 最近 12 轮没有新的改动或新信息。
反复出现：shell `curl http://127.0.0.1:#/rates` → Connection refused ×7
本任务改过：sync.py
  1  停下并总结（默认，直接回车）
  2  换个思路，再试 12 轮
  3  照原样继续
  或者直接输入新的指示
```

- `1` / 回车：走统一的收尾（下面）；
- `2`：给模型一条说明（"已经试过 X、Y，都失败在 Z；不要再重复这些做法，先说明阻碍，再换方向"），清零；
- `3`：清零，本任务的阈值翻倍（12 → 24 → 48），避免反复打扰；
- 其他文字：作为插话交给模型，清零。

**`-p`、没有终端、子 Agent**：直接走统一的收尾，然后结束任务。

**统一收尾**：现在的 `wrap_up` 加一个原因参数，调用上限和止损共用：
- 一次不带工具的模型调用（输出上限 1024 token，计费，计入会话），附上本地摘要，要求写清：做了什么、验证了什么、试过什么、卡在哪里、需要用户决定或提供什么；
- 总结失败不影响结束（和现在一样）；
- 任务状态记为中断（`Interrupted`，原因"没有进展，已停下"），`/continue` 可以接着做，计数重新开始；
- `TaskReport` 增加停止原因，`-p` 照样打印 `[summary]`，并加上"因连续 12 轮没有进展提前停止"（解决 P6）；调用上限结束时同样打印。

子 Agent：结束原因新增 `stalled`，结果第一行显示 `[exit: stalled, …]`，父任务据此决定要不要换做法。

### 5. 和现有机制的关系（合并，不叠加）

| 现有机制 | 改动 |
|---|---|
| guardrail（重复失败熔断） | 不变，继续警告和拒绝单次调用；被拒绝的调用算无进展 |
| 循环检测的三种模式 | 保留检测和拒绝；**删除** `hits`、第 2 次询问、第 5 次 `stopped` 这套升级（`guard.rs` 的 `hit`、`ask`、`STOPPED`、`MAX_HITS`、`ASK_AT_HIT`），拒绝的调用算无进展，由统一的进展计数决定何时停 |
| 60 次无活动提醒 | **删除**，由 6 轮提醒代替 |
| 调用上限 200 | 保留为硬上限和交互询问；结束时走统一收尾 |
| `VERIFY_ROUNDS = 3` | 保留；验证失败详情和上次相同时这一轮算无进展 |
| 失败批次升级（快速模型切主模型） | 保留；切换模型时清零一次，给新模型一个完整的窗口（D8） |
| 任务时限 | 不变 |

循环检测原来在第 2 次检测到时就会询问，可能早于 12 轮。合并后，连续被拒绝的调用每轮都算无进展，最晚 12 轮停；模型被拒后换了做法、拿到新结果，就不该停。

### 6. 模块划分

- 新增 `src/engine/progress.rs`：纯数据结构 `Progress`，`observe(round) -> Verdict { Progress, Idle(n), Warn, Stall }`，输入是本轮的工具调用、结果、是否被拒绝、验证摘要，不碰 IO，便于单元测试；
- `agent.rs` 的 `run_loop`：每批工具执行完（`pending` 之后）和每次催促之后调用 `observe`；`Stall` 时做快照确认，再询问或收尾。和调用上限的询问放在一起，共用 `self.user_input`；
- 子 Agent 走同一个 `run_loop`，自动获得这项检查；
- 工具结果是否被 hook 拒绝：`pending` 已经知道（`before_tool` 返回 `Some`），作为标志传给 `observe`，不靠解析 `[guardrail]` 前缀。

### 7. trace 和诊断

- 任务记录增加 `task_calls`（本任务的模型调用次数）、`idle_max`（最长连续无进展轮数）、`stalled`（是否因此停下）。`model_calls` 保留为会话累计值，以免和旧数据混淆（D7）；
- 新增诊断码 E5008"没有进展，已停下"，建议写"用 /continue 换个思路继续，或补上缺的外部条件"。

### 实施时的调整

都是小调整，没有改变方案的分工和阈值：

1. **第一次出现的错误算新信息。** 所以"同一条失败命令"要到第 13 轮才停：集成测试 1 的请求总数是 13 + 1 = 14，不是文档原写的 12 + 1。
2. **错误签名取错误的首行和末行，跳过 shell 的框架行**（`exit_code=…`、`stdout:`、`stderr:`、`[note:`/`[hint:`）。shell 结果的前两行永远是 `exit_code=… ` 和 `stdout:`，原定的"前两行"区分不了错误；Python 的 traceback 真正的错误在最后一行。
3. **`edit` 按整个输入（路径、old、new）判断是否见过**，不读文件算新内容的哈希：进展模块保持纯数据、不碰 IO；A→B→A 来回改照样认得出（单元测试覆盖）。`write` 按（路径，内容）。
4. **工作区快照在提醒那一轮（第 6 轮）也取一次，作为基准**；第 12 轮再取一次比较。只在第 12 轮取的话没有"本任务见过的树"可比。提醒时如果树已经变了，直接算进展、不发提醒。快照用新增的 `Snapshots::tree_now`：只暂存、不提交，超过 10 秒或自动快照已关闭时返回 `None`（跳过确认）；超时的暂存在后台跑完，不中途丢弃。
5. **子 Agent 不做快照确认**：子 Agent 的 hub 比快照存储先创建，拿不到它；按方案"快照不可用时跳过确认"处理。子 Agent 用 shell 改文件时可能被误判，见遗留。
6. **提醒作为一条单独的 notice 消息**放在这一轮工具结果之后，而不是改写最后一条工具结果：`History` 只允许追加，改写会让下一次保存写整份快照。
7. **止损摘要里没有"跑过的检查及结果"**：`Evidence` 在闸门层，引擎拿不到；摘要包含本次运行的模型调用次数、无进展轮数、出现两次以上的前 3 个错误（含被拦下的调用）和 write/edit 改过的文件。
8. **审批时用户写的理由不单独算"用户输入"**（被拒的调用本身不算进展）；插话、`ask_user` 的回答、止损询问里输入的指示算。
9. **实现方式**：调用上限和止损都走 `Error::Stopped(Box<Stopped>)`，带着 `TaskReport`；`app` 收到它先打印 `[summary]` 再返回错误（`-p` 退出码非 0）。子 Agent 按 `Stopped` 的种类给出 `max_iterations` 或 `stalled`，不再匹配错误文字里的"模型调用"。trace 字段通过新增的 `TurnHook::task_stats` 交给 `TraceHook`。`/doctor trace` 的任务行显示本次调用次数，没有进展时显示"没有进展"。
10. 阈值提醒用中文（方案原文），给模型的收尾请求和"换个思路"说明用英文，和其他系统通知一致。

### 删除的旧机制

`guard.rs` 的 `hits`、`stopped`、`ask()`、`hit()`、`clear_loops()`、`STOPPED`、`MAX_HITS`、`ASK_AT_HIT`、`STALL_THRESHOLD`、`since_activity` 和 60 次无活动提醒；`ToolGuard` 不再持有 `UserInput`（`ToolGuard::default()`）。原测试 `loops_are_refused_and_stop_after_five_detections` 改为 `loops_are_refused_and_other_calls_still_run`（只断言拒绝，停不停由进展计数断言）。`Exit::from_result` 里按文字匹配"模型调用"的分支删掉，改为匹配 `Error::Stopped`。
