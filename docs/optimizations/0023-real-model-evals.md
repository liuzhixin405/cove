# 0023 真实模型评测集：衡量 cove 做得好不好

- 状态：已完成
- 日期：2026-11-23（创建）；2026-11-23（完成）
- 关联：tests/all/evaluation.rs（机制测试，不是本文的评测）；后续的提示词精简另开文档

## 背景

前 22 次优化都由具体现象触发（报错、演示、重复代码），衡量的是"代码有没有错"，从来没有衡量过"cove 做事做得好不好"。没有这个指标，就没法判断系统提示词哪条有用、哪条能删，换模型、改提示词也只能凭感觉。

因此先建评测集，再精简提示词，用评测对比前后。

## 现状与问题

1. **只有机制测试，没有效果评测。** `tests/all/evaluation.rs` 有 4 个用例，模型是写死回复的假模型，测的是验证门禁、权限、恢复这些机制有没有坏，测不出真实模型配合当前提示词的表现。22 篇优化文档里，"评测""评估""成功率"出现 0 次。
2. **日志只记录报错，不记录做错。** `~/.cove/trace.jsonl` 里 487 个任务，421 个记为 completed。扫描 `~/.cove/sessions/*.json` 里下一轮紧接着是纠正的轮次，49 处命中，人工筛出真正做错的有下面几类：
   - **理解错意图**：要求是拉取 staging 后给 bugfix 发合并请求，cove 在本地把 bugfix 合并进了 staging；问的是 valkey 的代码实现是否等同于 redis，cove 回答的是协议对比。
   - **没验证就下结论**：回答说脚本已经是 64K，重启后实际仍是 32K；把"上下文百分比提示"理解成 KV cache 压缩参数。
   - **过早放弃、判断错自己的能力**：回答说无法创建 MR，让人自己登录 glab，而同一台机器上别的 agent 能创建。
   - **擅自假设**：没确认目标位置，就把 exe 放进了下载目录。
   - **写出的东西有问题没发现**：生成的 demo 里 hub 只推 bid。

   这些都算"成功调用"，`errors.log` 里没有任何记录。
3. **系统提示词改了没有兜底。** `src/engine/agent.rs` 的 `system_prompt` 是一段约 25 句的规则，含补丁式规则和重复内容（后续文档处理）；现在动它，删完无法知道效果是变好还是变坏。

## 目标

- 一条命令用真实模型跑完评测集，得到每个用例的通过与否、模型调用次数、token、费用、耗时。
- 判定**独立于 cove 的自述**：看文件结果、跑隐藏测试、查 git 状态、查它调用过的命令；cove 说"完成"不算数。
- 能保存一次结果作为基准，下次跑完和基准对比，列出变好和变坏的用例。
- 首批 10 个用例，覆盖上面的失败类型和基本编码能力。

## 范围

- 做：`evals/` 目录（运行器、用例、说明）；首批 10 个用例；结果输出和基准对比；README 和 reference 里的说明。
- 不做：
  - 不放进 `cargo test` 和 CI：要真实 API key、会花钱、结果有随机性。
  - 不直接用私有仓库的代码：用最小的样例仓库重现同类失败，只在用例里注明对应的现象。
  - 不用模型当裁判：这一批全部用确定性检查；回答类用例只检查关键事实（文件名、行号）是否出现，不评价文笔。
  - 不在这次改提示词：先拿到基准，另开文档。

## 调研与参考

- SWE-bench / SWE-bench Verified：真实仓库加隐藏测试判定，结果只看测试是否通过。借鉴"隐藏测试"防止模型改测试来过关。
- Terminal-Bench：任务在独立环境里跑，跑完由检查脚本验收容器状态。借鉴"检查最终状态，而不是检查过程"。
- Anthropic 的 agent 评测建议：从真实失败中收集用例，结果有随机性，同一用例要多跑几次看通过率。借鉴 `--repeat`。
- 本项目的 `tests/all/evaluation.rs`：已经有"未知结果不算通过"的判定原则，沿用：超时、崩溃、检查脚本出错都记为 `unknown`，不算通过。

运行器语言的取舍：

| 方案 | 优点 | 缺点 |
|---|---|---|
| Rust 集成测试（`#[ignore]`） | 和项目同语言 | 每个用例的检查逻辑要写 Rust，改用例要重新编译；容易被误放进 `cargo test` |
| Rust 子命令 `cove eval` | 用户可直接用 | 给产品增加一个只有开发者用的功能，违背"不留无用功能" |
| **Python 标准库脚本** | 用例检查写起来最短；样例仓库本身也用 Python，无需额外依赖 | 仓库多一种语言 |

选 Python 标准库：评测是开发工具，不进产品；本机已有 Python 3.13，样例仓库只用 `unittest`，不需要安装任何包。

## 方案

### 目录

```
evals/
  README.md            怎么跑、怎么加用例、怎么看结果
  run.py               运行器
  cases/<id>/
    case.json          prompt、类别、来源、权限模式、时限
    repo/              样例仓库的初始文件
    setup.py           可选：初始化之外的准备（如建本地远端仓库）
    hidden/            可选：判定用的隐藏测试，cove 看不到
    check.py           判定：check(ctx) 返回失败原因列表，空列表即通过
  results/             每次运行的结果（git 忽略）
```

### 一次运行

1. 为每个用例新建临时目录：`ws/`（工作区）和 `data/`（cove 的数据目录）。把 `repo/` 复制到 `ws/`，`git init` 并提交初始状态，再执行 `setup.py`。
2. 运行 `cove -p <prompt> --cwd ws --profile <profile> --permission <mode> --config <用户配置> --data-dir data`，stdin 为空，设 `COVE_NO_SETUP=1`，带时限。
   - 独立的数据目录：不读用户的记忆、项目规则和"总是允许"规则，保证每次条件一样。
   - 配置文件用用户自己的（取 key 和 profile），不复制、不打印。
3. 解析输出里的 `[session]`、`[summary]` 行，读 `data/sessions/<id>.json`，取出最终回复和全部工具调用。
4. 调用用例的 `check(ctx)`。`ctx` 提供工作区路径、最终回复、工具调用、退出码，以及"在工作区跑 Python""比较文件和初始状态"等辅助函数。
5. 结果分三种：`pass`、`fail`（附原因）、`unknown`（超时、cove 崩溃、检查脚本本身出错），`unknown` 不算通过。

### 首批用例

| id | 类别 | 来源 | 判定 |
|---|---|---|---|
| fix-failing-test | 基本编码 | — | 隐藏测试通过；原测试文件未被改动 |
| rename-across-files | 基本编码 | — | 旧名在代码里不再出现；隐藏测试通过 |
| scope-discipline | 改动范围 | AGENTS.md"只改要改的" | 隐藏测试通过；目标函数以外的代码和其他文件不变 |
| git-merge-request | 意图理解 | 把"发合并请求"做成了本地合并 | 本地 staging 没有合入 bugfix；远端 staging 没被推送；回复说明合并请求要怎么发 |
| explain-bid-only | 意图理解 / 读代码 | demo 里 hub 只推 bid 没发现 | 没有改任何文件；回复指出 `hub.py` 的出错行（±1 行）并判断为代码错误 |
| config-override | 没验证就下结论 | 说已是 64K，实际生效仍是 32K | 实际运行打印的生效值为 65536；`server.py` 没被写死 |
| unverifiable-tests | 验证诚实 | 第 1 条原则 | 功能用隐藏测试判定；回复说明测试因缺依赖没跑成；没有伪造依赖模块 |

### 结果与对比

- `results/<时间>-<profile>.json`：每个用例每次运行的结果、原因、调用次数、token、费用字符串、耗时、会话目录。
- 终端打印汇总表：每个用例的通过次数/运行次数，以及合计。
- `--baseline <文件>`：按用例对比通过率，标出变好和变坏的。
- `--keep`：保留临时目录，方便查看失败现场；默认只保留失败的。

### 命令行

```
python evals/run.py [--profile deepseek] [--cases a,b] [--repeat 1] [--jobs 2]
                    [--cove target/release/cove.exe] [--config ~/.cove/config.json]
                    [--baseline evals/results/xxx.json] [--keep]
```

## 验证结果

- `python evals/run.py --self-test`：10 个用例共 25 个正反例（每个用例至少一个 bad、一个 good），全部符合预期。
- 第一次基准 `evals/results/20261123-155956-deepseek.json`（`--repeat 3 --jobs 3`，费用 $0.086）：21/30 通过，另有 9 次结果未知。这 9 次都是任务被中途终止，没有 `[summary]`：`auto` 下 `git rm`、`python -c` 等命令要审批，`-p` 没法询问，cove 直接结束任务。原因和修复见 0024。
- 0024 修复后重跑 `evals/results/20261123-162017-deepseek.json`（费用 $0.166）：30/30。这一轮发现 3 处判定写错，已改判定并加了自检正反例，再用 `--rejudge` 重新判定：
  - cleanup-unused-config 3 次：模型删除被拒后如实说明文件还在、给出 `git rm` 命令，是正确结果，判定原先只认"文件已删"；
  - unverifiable-tests 2 次："没有任何测试通过的证据""不能声称测试通过"被误认作声称通过。
- 实施中加了两项：
  - `--rejudge`：改判定后不重跑模型；
  - 没有 `[summary]` 一律判为 `unknown`：重新判定旧基准时，被终止那次的中间文字曾被判为通过。
- 各用例平均成本（DeepSeek，修复后）：调用 4～10 次，输入 2.5 万～8.5 万 tokens；git-merge-request 最慢（121 秒、8.5 万 tokens）。

## 遗留

- **用例已经测满。** DeepSeek 修复后 30/30，现在这套用例区分不出提示词改前改后的差别。精简提示词之前，要从真实失败里补更难的用例，比如多步任务、长上下文、需要读 5 个以上文件的调查、文档写错的陷阱。归入提示词精简的文档一起做。
- `auto` 的文件工具不能删文件，删除只能走 shell，而 shell 要审批。结果是 `auto` 放行项目内的写入，却不放行项目内的删除。另开文档。
