# 优化文档

cove 的每一次改动（功能、修复、重构、性能），**先写文档，再改代码**。文档回答三件事：要解决什么、怎么解决、怎么算解决了。代码合并后，文档留作这次改动的记录，以后回看"当时为什么这么改"时查这里。

## 规则

1. **先文档后代码。** 文档写到"方案"和"验证"两节齐全，才开始改代码。需要拍板的点写进"待决策"，决定之后移到"决策记录"。
2. **一次改动一份文档。** 一份文档只解决一组相关的问题。改动中途发现新问题，另开一份，不往旧文档里塞。
3. **问题要有证据。** "现状与问题"写可以复现的事实：文件和行号、日志、数据统计、截图描述。不写"感觉不好用"。
4. **写清不做什么。** "范围"里列出这次刻意不处理的事和理由，免得范围悄悄扩大。
5. **完成后回填。** 改完把状态改成"已完成"，"验证结果"写实际跑过的命令和结果；没做到的写进"遗留"。
6. **小改动也写。** 一行的修复可以只写"问题、改法、验证"三段，但不能省略。

## 编号与文件名

`NNNN-简短英文标识.md`，编号从 0001 起依次递增，不复用。例如 `0001-unified-session-history.md`。新文档写好后在下面的索引里加一行。

## 状态

| 状态 | 含义 |
|---|---|
| 草稿 | 还在调研或等决策，不能开始改代码 |
| 已确认 | 方案已定，可以开始实施 |
| 实施中 | 正在改；分阶段的文档在"实施计划"里勾选进度 |
| 已完成 | 代码已合入，验证已回填 |
| 已放弃 | 不做了；写明原因 |

## 模板

复制下面的结构。每一节都要有内容；确实没有的写"无"并说明原因。

```markdown
# NNNN 标题

- 状态：草稿 | 已确认 | 实施中 | 已完成 | 已放弃
- 日期：YYYY-MM-DD（创建）；YYYY-MM-DD（完成）
- 关联：相关的文档编号、issue、demo 路径

## 背景
为什么现在要做这件事；用户原话或触发事件。

## 现状与问题
可复现的事实和证据（文件:行号、数据、截图描述）。每个问题编号，后文引用。

## 目标
做完以后用户能看到什么变化；可以检验的标准。

## 范围
- 做：……
- 不做：……（以及理由）

## 调研与参考
看过的同类实现、数据、方案对比，以及取舍理由。

## 方案
具体怎么改：数据结构、模块、接口、交互。分层或分阶段写。

## 影响范围
会改到的文件和模块；数据格式和兼容性；对现有行为的改变。

## 验证
怎么证明改对了：要新增或修改的测试、要跑的命令、要人工确认的界面。

## 实施计划
- [ ] 阶段 1：……
- [ ] 阶段 2：……

## 待决策
还没定的问题，以及每个问题的建议。

## 决策记录
- YYYY-MM-DD：决定了什么，由谁决定，为什么。

## 验证结果
（完成后填写）实际跑过的命令、结果、人工确认的结论。

## 遗留
（完成后填写）没做完或新发现的问题，以及去向（新文档编号）。
```
