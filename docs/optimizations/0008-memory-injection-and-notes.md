# 0008 记忆注入分层，删除会话笔记

- 状态：已完成
- 日期：2026-11-20（创建）；2026-11-20（完成）
- 关联：同类功能统一分析（第四组）；[0003](0003-remove-skill-auto-learning.md)（删除技能自动学习）

## 背景

同类功能统一分析的第四组。原计划是"会话笔记并入记忆；记忆注入从全量改成按相关性"。核查本机数据后发现两件事：

- 按相关性注入**已经有了**：记忆总量超过 24KB 时，就改为注入"索引 + 最相关的 8 条"。真正的问题出在这个模式的细节里，而且已经造成了实际影响（见 P1）。
- 会话笔记的内容质量很差，并入记忆只会污染记忆（见 P3）。

## 现状与问题

现在的注入规则（`memory/recall.rs` 的 `MemoryRecall::note`）：会话第一个任务（以及每次压缩之后）注入一次，之后只补充新增或改过的条目。

- 总量 ≤ 24KB：全部条目原文注入；
- 总量 > 24KB：注入一个索引（标题 + id，最多 6KB），再加上按 BM25 选出的最相关 8 条（每条最多 3KB）。

本机数据（111 个会话）：

| 项目 | 条目 | 正文 | 模式 |
|---|---|---|---|
| QuoteHub（`3a1cc4c0…`） | 161 | 215KB | 索引 |
| 其他 5 个项目 | 1–9 | 1–7KB | 全量 |
| 全局 | 3 | 1KB | — |

注入记录：首次注入 191 次，平均 10.7KB，最大 26.6KB；增量注入 31 次，平均 7.2KB。

**P1 索引被截断，全局记忆（包括"用户语言偏好"）被截掉。**
- 索引的顺序是先项目、后全局，项目内部按 id 排序。id 是随机的，所以等于随机排序。
- 161 条的标题写下来大约 16KB，索引只有 6KB，**91 次索引注入里有 69 次被截断（76%）**。被截掉的总是排在最后的全局记忆。
- 证据：91 次索引注入里，只有 22 次带上了全局条目。全局记忆一共 3 条：用户语言偏好、TMP 环境变量、cove 可执行文件的位置。
- 被截掉的项目记忆则是随机的一部分，跟新旧、跟本次任务都无关。

**P2 相关度只看本次请求的文字。** 请求是"继续""好的，按这个做"这类短句时，BM25 要么什么都匹配不到，要么只靠一两个常见词匹配，选出来的条目和实际要做的事无关。

**P3 会话笔记的内容质量很差。**
- 会话笔记（`session/notes.rs`）用正则表达式从对话里截取"决定"和"发现"，写进 `projects/<hash>/session_notes.md`，每个新任务按相关度附上最多 2KB，会话第一个任务另附最近 5 条。注入了 170 次，平均 683B。
- 内容样例（QuoteHub 的 66 行里）："格式差异就失败"、"`BY_REQUEST` |"、"一个小问题"、"文件开头这样写变量："、"后重做了一遍"、"本机系统语言，跟这次的改动无关"。大多是正则截断留下的残句，没有上下文就看不懂。
- 少数有用的条目，比如"两个 Postgres 同时监听 5432"、"Windows 版 redis-cli 输出到管道时不刷新缓冲"，正是记忆自动提取（用模型提取）要抓的内容。161 条项目记忆里，有 156 条来自自动提取。
- 它和记忆是两套"跨会话记住事情"的机制，存储、去重、注入、展示各写了一遍。

## 同类工具的做法（据公开文档）

- **Claude Code**（[memory 文档](https://code.claude.com/docs/en/memory)）：
  - `CLAUDE.md` 是用户写的说明，启动时整个加载；
  - 自动记忆分两层："`MEMORY.md` 是索引，每条一行，每个会话都加载（前 200 行或前 25KB，以先到者为准）"；每条记忆的详细内容放在单独的主题文件里，"启动时不加载，需要时由模型用文件工具读取"；
  - 索引接近上限时提醒模型压缩，超过上限时报错，要求重写索引，因为"超出部分下次加载时会被丢掉"；
  - 只和部分文件相关的规则可以按路径限定，用到匹配的文件时才加载。
- **Codex CLI**（配置参考）：项目说明 `AGENTS.md` 有字节上限（`project_doc_max_bytes`）；记忆功能默认开启，并"注入到之后的会话里"（文档没有说明挑选规则）。

可借鉴的地方：
- **始终加载的部分必须完整、可控**：Claude Code 给索引设了上限，超限时明确报错，而不是悄悄截掉；
- **详细内容按需读取**：cove 已经有 `memory` 工具的 `read` 和 `search`，模型可以自己去读。

## 目标

1. 全局记忆（用户的跨项目偏好）永远完整注入，不会被截掉。
2. 索引的顺序有意义：最近更新的在前；放不下的明确告诉模型"还有 N 条，用 memory search"。
3. 相关条目的挑选在请求是短句时不乱选。
4. 只保留一套跨会话记忆：删除会话笔记。

## 范围

- 做：
  - 改 `MemoryRecall::note` 的分层规则；
  - 删除 `session/notes.rs` 及其 hook、`/config memory` 里的显示和文档；
  - 用户数据：把 `projects/*/session_notes.md` 移到 `~/.cove/backups/0008-session-notes/`。
- 不做：

  - 不清理 QuoteHub 那 161 条记忆：那是 dream 的职责，靠规则删除容易误删；
  - 不改 embedding 的混合方式。

## 方案

**注入分三层**（只有总量超过阈值时才分层，不超过时仍然全部注入）：

| 层 | 内容 | 上限 |
|---|---|---|
| 1. 始终注入 | 全部全局记忆，原文 | 4KB；超出的条目进入索引 |
| 2. 相关条目 | 按 BM25（加上可选的 embedding）选出的项目记忆，原文 | 5 条，每条 2KB |
| 3. 索引 | 其余条目，每条一行"标题 (id 前 8 位)"，**按更新时间从新到旧** | 4KB；放不下时写"还有 N 条较早的记忆，用 memory search 查找" |

- **全部注入的阈值从 24KB 降到 8KB**：
  - 本机除 QuoteHub 外的项目都在 7KB 以内，不受影响；
  - 介于 8KB 和 24KB 之间的项目以后改为分层注入，避免第一个任务就塞进二十几 KB 的旧记忆。
- **相关条目的查询词**：本次请求不到 8 个字（"继续""好的"这类）时，改用会话标题加上一次请求作为查询词，仍然没有命中就不选。
- **索引里的 id**：模型读取记忆要用完整 id。索引只写前 8 位可以省一半空间，`memory read` 也要改成接受唯一的前缀（和 `/status agents` 的写法一致）。
- **预计大小**：以 QuoteHub 为例，全局约 1KB，加相关条目约 5KB，加索引 4KB，大约 10KB，和现在的平均值差不多。区别是全局偏好不会再丢，索引放的是最近的条目，而不是随机的一部分。

**删除会话笔记**：
- 删除 `session/notes.rs`、`Services.notes` 及其 hook、`/config memory` 里"会话笔记"一行、`reference.md` 里那一段；
- 已有的 `session_notes.md` 移到备份目录，不转换成记忆。理由见 P3：有用的内容自动提取已经抓到了，剩下的残句转进去只会污染记忆。
