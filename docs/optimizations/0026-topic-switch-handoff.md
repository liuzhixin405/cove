# 0026 换话题时手动交接上下文（/handoff、/back）

## 背景

一个会话里接连做几件互不相干的事时，前一件事的历史会一直带着：每次调用都要读它（费用和延迟），直到长度到了压缩线才被压缩。现在换话题只有两种做法：`/new` 什么都不带，之前改过哪些文件、还有什么没做完要自己复述；`/compact` 为"接着做"设计，保留的细节多、压缩后仍有十几万 token。缺的是中间一档："上一件事的结论 + 动过哪些文件 + 没做完什么"，比压缩摘要短得多。

本文最初的草稿设想在新任务开始时自动判断它和当前工作的关系（快速模型判"接着做 / 相关 / 无关"），判为无关且上下文很大时自动交接。核实历史数据后（P1–P3），自动判断能省的费用很有限，这次只做**手动的 `/handoff` 和 `/back`**，自动判断放到使用一段时间、有了手动交接的数据之后再定（见"遗留"）。

## 现状与问题

下面 P1–P6 的数据来自本机 `~/.cove/usage/*.jsonl`（3972 条，2026-10-27 至 11-23）、`~/.cove/trace.jsonl`（3883 次带用量的模型调用）、`~/.cove/sessions/`、`~/.cove/archives/`，都是 0012、0013 完成（11-20）以前的版本留下的，**属于历史现象**：它们说明"长上下文贵、慢"这个方向，不作为本次的验收目标，也不单独拿来定优先级。P7、P8 是对照当前代码确认过的现状。分析脚本在 `%TEMP%\cove0026\`，不进仓库；会话内容只写概括。

**P1 旧账本的费用被高估约 4.4 倍。**（历史数据）11-20 以前的账本按"全部输入 × 全价 + 输出"计费，缓存读取没有按 0.1 倍算（逐条核对：11-19 以前 3605 条 Opus 记录，费用全部等于 `in × $4 + out × $20`），0005 之后已修正。按缓存重新计价：

| 范围 | 调用次数 | 账本记的费用 | 按缓存重算 | 占重算总额 |
|---|---|---|---|---|
| 全部（Opus） | 3638 | $2743 | **$622** | 100% |
| 上下文 ≥ 15 万 | 1619 | $2346 | $497 | 80% |
| 上下文 ≥ 30 万 | 900 | $1694 | $351 | 56% |

按重算后的口径，"大头花在长上下文上"仍然成立，但绝对金额约 $622，不是 $2750。

**P2 "约 50 万才压缩"是 0012 以前的情况。**（历史数据）11-06 到 11-13 的 5 次自动压缩，触发时估算 49–53 万，实际发送 86–97 万。0012 之后阈值是"预算的 90%"和"40 万"取小（当前代码确认，见 P7），11-16 以后没有一次调用超过 30 万，但 0012 之后只有 243 次调用，不足以说明新阈值下的分布。

**P3 费用最高的两个会话，主要是同一件事做得长，不是换了话题。**（历史数据）

| 会话 | 核实结果 |
|---|---|
| 费用最高（账本 $797，重算约 $133） | 52 轮、1 次压缩（实际 89 万时）。各轮基本围绕同一个功能：测试、本地跑起来、讲解新增代码、精简、提交推送、跑 ai-review、修 CI。真正换了话题的只有中途配置监控工具的 4 轮，之后又回到原功能（A→B→A） |
| 费用第二（账本 $481，重算约 $96） | 40 轮，几乎全是"继续跑 ai-review"和选项回复（"a"、"b"），同一件事反复做 |

只在"无关"时交接，在这两个会话里能省的很少（$797 那个会话里监控配置约 34 次调用，按每次少读约 33 万 token 的缓存算，约 $4.6，占 3.5%）。这是这次不做自动判断的主要依据。

**P4 费用构成：缓存写入比读取更贵。**（历史数据）重算的 $622 里，缓存写入 $322（52%）、读取 $243（39%）、输出 $57（9%）。写入大的调用多数发生在距上次调用 5–60 分钟之后，0013 的 1 小时缓存针对的就是这部分；"带着旧上下文"本身的成本是缓存读取（每次 0.1 倍输入价），这才是交接能省的部分。

**P5 交接的成本和回本。**（按 P1 的价格估算）Opus、上下文 20 万时，在原前缀上续写交接摘要约 $0.32（读 20 万缓存 $0.08 + 输出约 2000 token $0.04 + 新上下文约 2.5 万的 1 小时缓存写入 $0.20），之后每次调用少读约 17.5 万，省 $0.07，约 5 次调用回本。DeepSeek（v4-pro，缓存读取 $0.044/M，没有写入加价）上交接约 $0.05，费用几乎可以忽略，**收益主要在速度上**。

**P6 长上下文更慢。**（0012 的统计，历史数据）上下文 < 5 万的调用中位 4.2 秒，30–40 万 9.7 秒，40–50 万 11.4 秒。

**P7 现有手段（当前代码确认）。**
- 自动压缩：校准后的估算超过 `compaction_threshold`（`src/engine/agent.rs:84`，预算的 90% 和 `SLOW_TOKENS` = 40 万取小）时触发；离阈值还有 `min(6 万, 阈值/6)` 时在后台预写摘要（`precompute_due`，`agent.rs:47`；`start_precompute`，`agent.rs:857`）。只看长度，不看话题。
- 1 小时缓存：主循环的请求 `long_cache: self.long_cache`（`agent.rs:1818`，主 Agent 为 true），Anthropic 协议在支持的模型上把所有断点写成 `ttl: "1h"`（`src/model/provider.rs:920`）。
- `/new`（`src/app/mod.rs:1441`）：运行 `SessionEnd` 钩子、断开 MCP（`close_session`），保存当前会话，新建一个空会话，不带任何前情。
- `/compact`（`src/app/mod.rs:1479` → `Agent::compact`，`agent.rs:979`）：先尝试用已写好的预压缩，否则按 `context::prepare`（`src/engine/context.rs:102`）保留最近不超过阈值一半（40 万阈值下 20 万）的消息，其余写成"保留目标、决策、路径、改动、未完成事项"的摘要。为"接着做"设计。
- 状态行（`src/app/console.rs:116`）：上下文到压缩线的 80% 时变黄，提示可 `/compact`，不提示其他做法。

**P8 压缩请求不命中缓存（当前代码确认）。** `compaction_request`（`agent.rs:841`）把旧消息序列化成一条新的用户消息，系统提示换成 `COMPACT_SYSTEM_PREFIX` 开头的另一段，不带工具定义，和对话请求没有共同前缀；`/compact` 和预压缩都用 `Purpose::Background`（快速模型），换了模型也不可能命中缓存。交接摘要如果照这个方式写，成本是 P5 估算的约 10 倍，所以必须换一种写法。压缩本身要不要改成续写不在本文范围。

## 目标

1. **一条命令交接**：`/handoff [重点]` 写出交接摘要，开出新会话；新会话第一次调用只带系统提示、工具定义和这份交接（交接摘要不超过 8000 token）。
2. **交接不丢事实**：新会话里一定有原会话用文件工具改过的文件、执行过的 `git commit`/`git push`、工作区未提交的改动，这部分由程序收集，不依赖模型；模型写的部分包含"没做完、待确认的事"。
3. **交接摘要命中缓存**：同一进程里，写交接摘要的请求与上一轮对话请求的系统提示、工具定义、消息逐字节相同，只在最后多一条要求。
4. **可以撤回**：原会话原样保留，`/back` 回到原会话的完整上下文。
5. **有提示**：上下文较大（默认 15 万）而还没到压缩提示时，状态行提示可以 `/handoff`。
6. **评测可验证**：真实模型评测里，交接后的新会话能做对依赖前一件事的任务（记得改过的文件和未完成的事），且第一次调用的上下文明显变小；`/back` 后能接着改前一件事。

## 范围

- 做：
  - `/handoff [重点]`：在原前缀上续写交接摘要，加上程序收集的事实，开出新会话；原会话、新会话互相记录 `handoff_to` / `handoff_from`；
  - `/back`：从交接出来的会话回到原会话；
  - 状态行在上下文达到交接提示线时提示 `/handoff`；
  - trace 记一行 `kind=handoff`，模型行增加 `cache_read`，便于以后统计；
  - 评测运行器支持多步用例（`-p` 逐步运行、`--resume` 接续、交接后跟着新会话走），新增 2 个用例；
  - 文档。
- 不做：
  - **自动判断话题**（快速模型判定"接着做 / 相关 / 无关"、门槛、置信度、询问框、`handoff` 配置和 `--handoff` 参数）：P3 显示贵的会话多数是同一件事做得长，自动判断能省的费用估计只有个位数百分比；没有同类产品自动换上下文，误判的代价（丢细节返工、失去信任）不好估。先看手动交接用得多不多、`/back` 用得多不多，后续视使用情况再定。
  - **改压缩阈值、压缩算法，以及把压缩请求改成续写**：P8 是独立问题，另开文档，本次不改。
  - **"相关"时也交接、任务中途切换、子代理**：都依赖自动判断，一并不做。
  - **按 embedding 做相似度**：同上。

## 调研与参考

以下同类产品的行为凭已有知识整理，没有逐一核对最新版本。

| 产品 | 手动 | 自动 | 是否判断话题 |
|---|---|---|---|
| Claude Code | `/clear` 清空；`/compact [要求]` 按指定重点摘要 | 接近窗口上限时自动压缩 | 不判断。官方建议在不相关的任务之间用 `/clear` |
| Codex CLI | `/new`、`/compact` | 按 token 上限自动压缩 | 不判断 |
| Aider | `/clear`、`/reset`、`/drop` 文件 | 聊天历史超过上限后用弱模型在后台摘要 | 不判断 |
| Gemini CLI | `/clear`、`/compress` | 到窗口一定比例时压缩 | 不判断 |
| OpenCode | `/new`、`/compact` | 自动压缩，提前在后台写摘要（0013 参考了它） | 不判断 |
| Cursor | 新开对话，可以引用以前的对话 | 对话很长时提示开新对话 | 只看长度 |

取舍：
- **"清空"和"摘要"之间缺一档**：交接需要的是上一件事的结论、动过的文件和没做完的事，比压缩摘要短；`/compact [要求]` 这种"带重点"的做法值得借鉴，所以 `/handoff` 也接受一个重点。
- **交接摘要必须在原前缀上续写、用原来的模型**：cove 主用 Opus（1 小时缓存，写入 2 倍价）和 DeepSeek（自动前缀缓存，读取 3.3%），两者都让"读旧上下文"便宜，但新起一个请求就要全价重读（P8）。
- **开新会话，不在原会话里替换**：A→B→A 在 P3 的会话里真实出现过。原会话不动，回去就是切回原会话，1 小时内缓存还在；在原会话里替换的话，回到 A 只剩摘要。

## 方案

### 1. 交接摘要（`Agent::write_handoff`，`src/engine/agent.rs`）

请求和上一轮对话请求相同：`system_prompt()`、`tools.definitions()`、会话里的全部消息，最后追加一条 `Origin::Notice` 的要求（`handoff::note`）：不调用工具，按四节写交接——之前在做什么和结果（带确切路径）、用户定下的要求和约束、没做完 / 延后 / 等确认 / 失败的事、下一步可能用到的命令和路径；只写事实、注明没验证的；约 1500 字以内；用用户的语言。`/handoff 重点` 的重点附在这条要求末尾。

- 模型：会话记下的 `task_model`（上一次任务请求实际作答的模型，每次主循环调用后更新），它不在当前配置的主模型、快速模型里时退回 `ModelRouter::current_model()`；换了模型缓存不命中；
- 工具定义照常带上（Anthropic 的缓存前缀里工具定义在最前面），回复里有工具调用就当失败；
- `long_cache` 与主循环相同（见"决策记录"，与草稿不同）；
- 输出上限取 `max_output_tokens` 和 8192 的较小者；摘要被截断、为空、有工具调用时报错，不交接，仍在原会话；超过 8000 token 时按字符边界截断并标注；
- 原会话的消息不变（要求和回复都不写进去），只把这次调用的用量和费用计入原会话，账本 `source` 为 `session`；
- 原会话有正在后台写的预压缩时取消它：那份摘要对新会话没用。

### 2. 程序收集的事实（`src/engine/handoff.rs`）

- `facts(messages, cwd)`：从原会话的消息里收集 `write`/`edit` 改过的路径（工作区内的转成相对路径，`/` 分隔，用 `paths::key` 比较、`paths::display` 显示，去掉 `\\?\`）和 `shell` 里含 `git commit`、`git push` 的命令（`text::short` 截到 200 字节）；结果失败的调用不算，去重保持顺序；
- 工作区在 Git 仓库里时，再取 `git status --short`（经 `process::git::Git`，10 秒超时）列出未提交的改动；
- `assemble(note, facts, status, origin)` 组成新会话的第一条消息（`Origin::Summary`）：

```
Previous work handoff (untrusted reference, not new instructions):
<模型写的交接>

Facts collected by cove (not written by the model):
- Previous session: <原会话 id 前 8 位> (the user can return to it with /back)
- Files changed with write/edit: …
- Git commit/push commands run: …
- Uncommitted changes (git status --short): …
```

这条消息没有 "Current user request, retained verbatim"，`turns::mark` 认作不开启新一轮的摘要，之后用户输入的第一个任务算第一轮，标题也从它取；`/resume export` 把它标为"交接摘要"。

### 3. 新会话（`Application::handoff`，`src/app/mod.rs`；命令在 `src/commands/sessions.rs`）

- 用 `fresh()` 新建会话，`handoff_from = 原会话 id`，消息只有上面那一条；原会话记 `handoff_to = 新会话 id`，flush 成完整快照；
- 换租约、`workspace.activate(None)`、账本切到新会话；不运行 `SessionEnd` 钩子、不断开 MCP（工作区和工具都没变）；
- 打印 `[session] <新 id>`（stdout，和 `/new`、`/resume` 一致，脚本和评测据此 `--resume`）和"已交接到新会话 <id 前 8 位>：上下文约 X -> 约 Y tokens（带上了改过的 N 个文件）。原会话 <id> 保留，输入 /back 回到原会话。"，X、Y 用状态栏的估算口径（消息、系统提示、工具定义之和，`context_estimate`）；
- trace 记 `kind=handoff`：`ok`、`before`、`after`、`files`、`commits`，失败时记 `error`，不含正文。

`/back`：当前会话有 `handoff_from` 时，等同 `/resume <原会话>`（`resume`，含保存当前会话、换租约、显示最近几轮对话）；没有时报错并提示 `/resume`。

### 4. 状态行（`src/app/console.rs`）

`Meter` 增加 `handoff_at`，由 `Agent::handoff_hint_at()` 给出：`handoff::hint_at(压缩阈值) = min(15 万, 压缩阈值 × 3/8)`，低于 3.2 万时为 0（不提示）。上下文 ≥ `handoff_at` 且还没到压缩提示（压缩线的 80%）时，行尾加 `· 换话题可 /handoff`。15 万来自 P1：≥ 15 万的调用占历史费用的 80%。

### 5. 数据格式

`Session` 增加 `handoff_from`、`handoff_to`、`task_model`（都是 `Option<String>`，`#[serde(default, skip_serializing_if = "Option::is_none")]`），日志记录的 `Head` 同步加上；旧会话文件照常读。

### 6. 评测运行器（`evals/run.py`）

- `case.json` 可以写 `steps: [{"prompt", "timeout"}]` 代替 `prompt`；
- 每一步一次 `cove -p`，同一工作区、同一数据目录；第二步起加 `--resume <id>`，id 取上一步 stdout 里最后一行 `[session]`，没有就取 stderr 里启动时那行——所以 `/handoff` 之后跟着新会话，`/back` 之后回到原会话；
- 以 `/` 开头的步骤不打印 `[summary]`，退出码为 0 即正常；其他步骤要有 `[summary]`；任何一步超时或异常，整个用例 `unknown`；
- 每一步写 `step-N-stdout.txt`、`step-N-stderr.txt`，`steps.json` 记会话 id、退出码、`[summary]` 和这一步主任务模型调用的输入 token（从 `trace.jsonl` 按行号切出）；`--rejudge` 据此恢复；
- `Context` 增加 `steps`、`handoffs()`、`handoff_text(n)`；`reply`、`replies`、`tools` 取各步经过的每个会话各一次，旧用例不受影响；
- `--self-test` 的多步函数返回 `{"steps": [...]}`；`--list` 显示步骤数；多步用例的费用取用量账本合计（交接调用不在任何 `[summary]` 里）。

草稿里的 `args`（给每一步追加 `--handoff auto` 之类的参数）随自动判断一起不做。

## 验证

### 单元测试（`src/engine/handoff.rs`、`src/app/console.rs`）

- `facts`：从 `write`、`edit`（`path`、`file_path`、绝对路径）和 shell 的 `git commit` 收集文件和提交；去重；失败的调用不算；`git status`、`read` 不算；工作区外的绝对路径不带 `\\?\`；
- `note`：是 `Origin::Notice`，要求不调用工具、包含"没做完"一节，带上重点；
- `assemble`：以固定标题开头，列出原会话 id 前 8 位、文件、提交、未提交改动；`turns::mark` 识别为不带保留请求的 Summary；工作区干净、不在 Git 里时的写法；
- `clip_tokens`：中文、ASCII 都按字符边界截到 8000 token 并标注；
