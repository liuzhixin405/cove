# 性能优化建议

本文记录 cove 任务响应慢的可能原因、优化方向和验证方法。代码路径说明的是当前实现，不代表某次慢任务已确认的根因。应先采集分阶段耗时，再按影响排序实施优化。

## 已落地

### 按任务规模选择并行拆分

主 Agent 的系统提示现在明确了任务选择规则：至少三项实质且相互独立的工作，使用 `todo` 和 `execute_plan` 并行执行；通过依赖声明表达先后关系。简单任务和“提交后推送”等串行流程留在主任务，避免子 Agent 启动、协调和汇总的额外成本。并行完成后检查合并结果，只运行相关检查。

提示词位置：`src/engine/agent.rs` 的 `Agent::system_prompt`。

## 当前实现中已有的提速机制

- 同一轮模型响应中的连续只读工具（`read`、`glob`、`grep`、`repo_map`）最多并发 8 个，结果按原顺序记录。实现位于 `src/engine/agent.rs` 的 `pending` / `run_concurrent`。
- `execute_plan` 按依赖图调度独立子任务；默认最多并行 4 个，文件写入认领用于避免两个计划项同时写同一文件。适合多块、耗时且边界清晰的工作，不适合很小的修改。
- 后台 Agent 可让长任务在独立 worktree 中运行，主任务不必等待；后台完成使用通知机制，不需要周期性轮询。
- `repo_map` 缓存文件解析结果，未命中缓存的文件可并行解析。
- 新任务的 Git 上下文用一次 porcelain v2 状态查询获取分支、HEAD 和改动；HEAD 未变时复用近期提交列表，避免重复启动多个 Git 子进程。

这个 Git 上下文优化已实装；静态上从通常的三次 Git 子进程启动减少为一次（状态变化但 HEAD 未变时仍为一次；只有 HEAD 改变才额外查询日志）。实际耗时取决于仓库和文件系统，尚未做环境基准测试。

## 优化候选

### 1. 缩短模型往返链路

**为什么可能慢：** Agent 每轮向模型发送当前系统提示和消息历史，接收工具调用后执行，再把结果交给模型决定下一步。每一次额外模型轮次都增加 API 延迟；上下文变长时，重复发送和模型处理也更重。提交、推送、等待等短 Git 命令如果分别触发模型轮次，等待时间可能主要花在模型服务端，而非 Git。

**现有观测：** `/doctor trace` 已记录每轮模型请求的总耗时、输入/输出 token、工具调用数，每个工具调用的耗时，以及任务总耗时；轨迹不包含消息正文。用它检查是否有重复轮次、过长上下文或明显较慢的工具。

**建议：** 继续通过提示词要求同轮批量读取，并在无需查看前一步结果时一次发出多个独立只读调用。若 trace 显示模型轮次是主要耗时，再考虑进一步减少往返。对确有连续后置步骤的工作流，评估专用的受控工作流工具，避免为了减少往返而把可能失败的命令盲目预先排队。

**注意：** 不能在提交未成功时仍继续推送。减少模型轮次不能绕过逐项授权，也不能让写操作或外部副作用并发执行。

### 2. 按需生成或缓存项目大纲

**当前行为：** 程序组装项目上下文时调用 `outline` 遍历工作区，最多处理 20,000 个条目；当前会跳过 `.git`、受保护路径和部分常见构建目录。项目上下文在启动组装阶段生成。

**建议：** 先测量该遍历的耗时。若大型仓库启动时占比明显，再考虑缓存大纲、按需扫描，或依据 ignore 规则缩小扫描范围。缓存需要有明确失效策略，不能让模型长期看到过期的目录结构。

**预期收益：** 主要改善启动或首个任务的等待；对每轮模型 API 的等待不会有直接帮助。

### 3. 并行计划的任务边界与调度

**建议：** 仅在拆分和协调成本低于并行收益时使用计划执行。每个子任务应有独立目标、明确文件/接口边界和可复核结果；把真正依赖的步骤写入依赖图，让不相关项尽早启动。避免多个任务争抢同一文件、同时运行昂贵的全量检查，或把最终集成和验证也重复分散给多个 Agent。

**验证：** 比较同类任务的总耗时、模型调用数、冲突重试数和最终检查次数，而不只比较子任务完成时间。

### 4. 区分 Git、网络与远端等待

**建议：** 对 Shell 命令和 Git 操作分别记录开始/结束时间，并区分 `git push` 完成时间、CI/远端检查等待时间、用户审批等待时间和模型请求时间。用户说“推送然后等待”时，应确认具体等待阶段。当前静态检查没有确定某次延迟来自推送、CI、审批还是模型 API。

**后续优化方向：** 如果 Git 本地耗时高，再调查钩子、索引和仓库规模；如果 push 慢，调查 DNS、代理、认证和远端；如果命令已完成而任务仍在等待，检查模型轮次或明确的等待工具。

### 5. 让用户看到等待发生在哪一段

**现有观测：** `/doctor trace` 已能查看模型、工具和任务耗时；Shell 工具的计时包含命令执行期间的授权等待。它没有单独标记授权时间、命令类型、Agent 协调时间或启动时的上下文扫描时间。

**建议：** 先用现有轨迹定位主要耗时段。若仍无法区分 Git、授权或启动开销，再补充不含命令正文的阶段计时，例如安全的工具类别、单独的授权等待和项目上下文生成耗时。

**预期收益：** 这项改进主要提高可诊断性；采集到实际数据后，再实施更有把握的性能改动。

## 推荐顺序

1. 用 `/doctor trace 100` 从慢任务收集现有模型、工具和任务耗时，建立基线。
2. 优先减少重复模型往返和不必要的全量检查；保留失败后的停止条件和授权语义。
3. 测量大仓库启动扫描；只有它是明显耗时来源时才做缓存或延迟扫描。
4. 对适合并行的多项工作比较串行与 `execute_plan` 的总耗时和冲突率。
5. 根据数据调整 Git、网络或远端等待路径。

## 测量口径

选择包含简单问答、单文件修改、多文件修改、并行计划、提交/推送的代表性任务。记录端到端时长，并拆分：

| 阶段 | 记录内容 |
| --- | --- |
| 启动 | 项目上下文/大纲扫描耗时（当前未单独记录） |
| 模型 | 每轮总响应时间、输入/输出 token、轮数（`/doctor trace` 已记录；未记录首 token 时间） |
| 工具 | 工具名称、总执行时长（`/doctor trace` 已记录；Shell 命令阶段未分类） |
| 并行 | Agent 数、重叠运行时间、文件冲突与重试 |
| 检查 | 执行的检查命令、时长、是否重复 |
| Git/远端 | add、commit、push 各自耗时，以及 CI 或人工等待时长（需要额外分类或外部记录） |

对同一类任务至少重复数次，并记录模型、服务商、网络/代理和仓库状态。一次结果容易受模型负载和网络波动影响，不宜据此判断优化是否有效。
