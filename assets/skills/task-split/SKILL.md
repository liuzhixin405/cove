# 拆分并行（task-split）

目标：长任务不再串行地等。把任务拆细、并行做，**中间不复制目录、不建分支**，最后统一验证一次。拆分这一步决定后面的走向，宁可多花一点时间分析，也不要草率开工。

## 什么时候用

- 预计超过 5 分钟（第二步估算），并且至少有两块工作可以同时做。
- 用户明确要求"拆开并行""分给几个 agent 一起做"。

## 什么时候不用（直接按普通方式做）

- 预计不到 5 分钟，或者拆不出两块可以同时做的工作。
- 调试型任务：要边跑边看、一步步缩小范围。
- 改动集中在一个文件或一个函数里，或者各块之间耦合很紧、互相依赖。
- 需求本身还不清楚：先问清楚，再决定。

## 第一步：分析

1. **澄清**：用一两句话重述目标，写出验收标准（怎样算做完）。有不确定、会影响拆法的地方，先问用户；需要大范围查代码时，同时派几个只读的调查子 Agent。
2. **影响分析**：找出要改的模块、文件和符号（函数、类型、方法），谁调用它们，哪些测试覆盖它们。能用代码索引、调用方分析的就用，不要凭印象。
   - 产出：每处改动的**写集合**（会改的 `文件` 或 `文件::符号`）、**读集合**（要看懂的）、相关测试。

## 第二步：判断值不值得拆

- **估算时长**，按这几项累加：改动的文件和符号数量；相关测试、构建的实际耗时（项目里有验证记录或 CI 记录的，用实际数字）；要不要等外部的东西（CI、部署、人工审批）。
- 估算超过 5 分钟、并且能拆出至少两块可以并行的工作，才继续往下拆；否则写一句理由，按普通方式做。
- **每多一个单元，就多一份固定开销**：子 Agent 看不到主对话，要重新读背景，大约要 1 万 token 和半分钟。单元太小会得不偿失。

## 第三步：拆分

1. **先定接口，再并行**：几块工作都依赖一个新接口、新类型或新数据结构时，先拆出一个"**契约单元**"，只定签名、类型和数据结构，或者先写好接口文档。实现单元和测试单元都依赖它，在它完成后并行。这是真正能拆开的关键。
2. **单元粒度**：一个单元是一处连贯的改动，大约一个函数到几个文件，几分钟能做完。太小的就合进相邻单元。
3. **每个单元写一张卡片**：

   | 字段 | 内容 |
   |---|---|
   | 编号、标题 | `U1 新增 VendorBackoff 配置项` |
   | 目标 | 一两句话，写清楚要做到什么 |
   | 写集合 | 只允许改的文件或 `文件::符号`；**不在里面的一律不准改** |
   | 读集合 | 要先看懂的文件 |
   | 依赖 | 前置单元的编号 |
   | 完成标准 | 不跑全量测试，怎么判断它做完了：比如编译通过、某个函数签名就位、新增的测试用例写好了 |
   | 预估 | 分钟数 |

4. **测试也拆成单元**：测试单元依赖契约单元，而不是依赖实现单元，这样能和实现同时写。

## 第四步：冲突和资源检查

- **写集合有重叠**：两个单元要改同一个文件、同一个符号时，要么合并成一个单元，要么排成先后依赖（后一个在前一个的结果上改）。**并行的单元之间，写集合必须互不重叠。**
- **会生成或改写文件的步骤**，单列为合并之后的串行步骤，不放进并行单元：代码生成、数据库迁移、`npm install`/`dotnet restore`、格式化工具、改锁文件。
- **用共享资源的步骤**也放到最后串行做：构建锁、端口、测试数据库、外部服务。
- 有关键路径的，标出来。

## 第五步：自检，然后交给用户确认

自检，逐条过：

- [ ] 每条需求和验收标准都落到了某个单元。
- [ ] 每个单元都有写集合和完成标准。
- [ ] 并行的单元之间，写集合互不重叠；重叠的已经排了先后。
- [ ] 契约单元排在依赖它的单元前面。
- [ ] 生成文件、用共享资源的步骤都放到了最后。
- [ ] 单元不会太碎：每个单元都值它的固定开销。

然后把计划交给用户，等用户确认（用户可以改、删、合并单元，或者选择不拆）：

```text
目标：……
验收标准：……

| 单元 | 写集合 | 依赖 | 完成标准 | 预估 |
|---|---|---|---|---|
| U1 契约：…… | src/a.cs::IFoo | — | 接口编译通过 | 3 分钟 |
| U2 实现 A | src/a.cs::Foo | U1 | …… | 6 分钟 |
| U3 实现 B | src/b.cs | U1 | …… | 5 分钟 |
| U4 测试 | tests/FooTests.cs | U1 | 用例写好 | 5 分钟 |
| 收尾（串行） | — | U2–U4 | 构建、测试、审查通过 | 8 分钟 |

串行预计 27 分钟；并行预计 17 分钟（关键路径 U1 → U2 → 收尾）。
单元数 4，额外开销约 4 万 token。
风险：……
```

## 第六步：并行执行

**默认在同一个工作目录里并行**，不复制目录、不建 worktree：写集合互不重叠，就互不干扰。

- **cove**：用 `todo` 写计划，每个单元一条：`id`、`depends`（依赖）、`writes`（写集合：文件路径或 glob，可以写成 `文件::符号`）、`estimate_minutes`（预估分钟数），内容里写上单元卡片的其余部分；收尾的串行步骤不放进这个计划，等合并之后由你自己在主工作区做。然后**优先**调用 `execute_plan`，参数 `parallel=true isolation="overlay"`（同时最多 `max_agents` 个，默认 4；cove 会先把计划交给用户确认）：
  - 每个单元都必须写 `writes`。每个单元在自己的覆盖层里改，全部结束前主工作区不变；同一个文件、写了不同 `::符号` 的单元也并行，其他重叠由 cove 自动排成先后（后一个在前一个的层上改），结果里会写明。
  - 单元里不能跑构建、测试和会写盘的命令（只放行只读命令，而且看不到层里的改动），`write`、`edit` 也只能改写集合里的文件；配置了 `overlay_check` 时单元多一个 `check` 工具，可以在共享检查槽里编译。
  - 全部结束后 cove 按依赖顺序统一合并（直接写入、行级合并、经校验的锚点重放、结构化合并），作为一个检查点（`/diff`、`/undo` 可用）；有冲突的单元会自动基于合并后的内容重做一次，仍冲突的文件不写入，结果里列出带冲突标记的副本，由你处理。
  - 合并之后，你在主工作区跑一次第四步列出的串行步骤，再统一构建、测试和审查。
  - 不适合覆盖层的情况（单元必须边跑边看、要跑生成文件的命令、用户不同意），改用 `isolation="main"`：单元直接在主工作区改，并行的条目写集合重叠时整个计划在开始前被拒绝；写集合以外的 `write`/`edit` 和包安装、代码生成、格式化类命令照样拒绝，shell 越界改动只报告。
- **Claude Code**：在同一条回复里同时发起多个子 Agent（Agent 工具，`general-purpose`），不加 `isolation`。有依赖的单元，等前置单元完成后再发起。
- **Copilot CLI**：用 `/fleet`，或者同时发起多个子代理；它们本来就共用同一个目录。
- **只有这两种情况才用 worktree**：用户想要每个单元各出一个分支；或者某个单元必须边跑边看，而且会改共享文件。cove 用后台 Agent（`agent {background: true}`）；Claude Code 用 `isolation: "worktree"`。

**发给每个单元的提示词**（子 Agent 看不到主对话，要写全）：

```text
你负责单元 U2：<标题>。
背景：<目标、相关设计、契约单元已经定好的接口（贴出签名）>
写集合：只能改 <文件/符号>。其他文件只读；发现必须改别的文件，停下来说明原因，不要自己改。
读集合：<文件>
完成标准：<……>
规则：
- 不要跑全量构建和测试，它们在所有单元合并后统一跑一次。可以做本单元的轻量检查，比如单个文件的语法检查。
- 不要运行会生成或改写文件的命令：代码生成、迁移、包安装、格式化工具。
- 结束时报告：实际改了哪些文件（逐个列出）、完成标准是否满足、没做完的和你的担心。
```

## 第七步：合并

- **同一目录模式**：不需要合并。逐个核对单元报告里实际改了哪些文件，并用 `git status`、`git diff --stat` 确认。**超出写集合的改动**要检查：会不会和其他单元冲突，是不是越界。
- **worktree 模式**：按依赖顺序合回主工作区。
  - 同一个文件被多方改过时，用三方合并：`git merge-file -p --diff3 <当前> <基线> <单元的版本>`，在临时文件上做，不需要建分支。
  - 合并有冲突的那一处，不要猜：把主工作区的当前内容和冲突说明交给原单元（或者一个新的单元），让它基于当前内容重做那一处。

## 第八步：一次性验证和收尾

1. 先跑第四步列出的串行步骤：代码生成、迁移、包安装、格式化。
2. 跑一次完整的构建和测试；项目有审查命令的，也跑一次。
3. 失败的，在主工作区按普通方式修，修完重跑。
4. **不自动提交**，提交由用户决定。
5. 汇报：
   - 每个单元的结果：完成或没完成，实际改了哪些文件；
   - 合并情况：有没有越界改动、冲突怎么处理的；
   - 验证结果：跑了哪些命令，实际输出是什么；
   - **预估和实际的对照**：每个单元、总时长、费用。这能帮下一次估得更准。

## 常见错误

- 拆得太碎：每个单元的固定开销超过它省下的时间。
- 并行单元的写集合重叠，"大概不会冲突"：必须排先后，或者合并成一个单元。
- 没有契约单元，几个实现单元各自发明接口，最后对不上。
- 让单元各自跑全量测试：多个单元抢构建锁和测试资源，比串行还慢。
- 在单元里跑代码生成或包安装，改了别人写集合里的文件。
- 合并冲突时直接选一边：冲突要交给知道意图的单元重做。
